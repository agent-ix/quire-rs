## Summary

This analysis scored US-019, FR-069..FR-072 and NFR-021 on technical risk, volatility and implementation complexity against the current loader (`src/loader/{manifest.rs,mod.rs,compile.rs}`, jsonschema 0.18.3 with the `resolve-file`/`wasm` feature split), the parser AST (`src/ast.rs`), the Filament extraction API (`src/filament.rs`, `src/python/mod.rs`, `quire-wasm/src/lib.rs`) and `src/validate_document.rs`. The slice is well-bounded in intent but three requirements hide design decisions the AC tables do not size: FR-071 assumes parser fence offsets that do not exist, FR-070 assumes a bundle index that none of the single-document surfaces receive, and FR-069 requires an offline `$ref` resolver and an embedded semantic-core bundle whose location and embedding mechanism are unstated. Verdict: proceed to planning with FND-380..FND-382 resolved as explicit design items (ADR or plan tasks) before task decomposition; nothing here blocks the spec.

## Top Hazards

1. FR-071 spans need a parser AST change nobody has scoped; done carelessly it changes `parseDocument` bytes and fails NFR-021-AC-3 (FND-380).
2. FR-070 type resolution has no bundle to resolve against on the Filament, Python and WASM surfaces; parity could pass on placeholders while the compiler gets no real identities (FND-381).
3. FR-069 offline `$ref` resolution and semantic-core embedding under the `wasm` feature are unimplemented mechanisms in jsonschema 0.18.3 as configured; the resolver, the embedding layout and the toolchain digest algorithm must be settled before any load-time task is written (FND-382).
4. Byte-identity tests are only meaningful against a baseline captured from `main` before implementation begins (FND-385).
5. The WASM parity leg is blocked by a stale git-branch pin in `quire-wasm` (FND-384).
